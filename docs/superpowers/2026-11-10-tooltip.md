# Tooltip

**Date:** 2026-11-10
**Changes:** uncommitted in the working tree.

## Goal

Build `<cc-tooltip>` from the Figma "Tooltip" component set (file `K7Z7bb2IjqiyDjik5qjEoN`, set `513:590`). The linked node `384:1190` is the documentation frame. The plan (Wave B) says to build it on the Popover API, with anchor positioning.

## Requirements

### From Figma

- **Properties:** Direction (Top, Bottom, Left, Right) is the side of the trigger the tooltip sits on, and the arrow points back at the trigger. The text is a text property ("Tooltip content").
- **Bubble:**
  - fill `Surface/surface-black`, radius `radius` (4px);
  - padding `padding - 0,5` / `padding - 1` (4px / 8px), so it is 28px tall;
  - text `Label/medium` regular (14/20) in `Text/high-emphasis`.
- **Arrow:** a 16×8 triangle in the bubble's colour. It overlaps the bubble by 2px, so 6px sticks out, centred on the side facing the trigger.
- No states, no shadow, no maximum width.

### Behaviour (WAI-ARIA tooltip pattern, WCAG 1.4.13)

- It shows on hover and on keyboard focus of the trigger, and hides on pointer leave, blur and Escape.
- **Hoverable:** the pointer can move from the trigger onto the tooltip without it closing.
- It describes the trigger: screen readers read the text as the trigger's description, not as its name.
- It isn't clipped by `overflow: hidden` ancestors, and stays attached to the trigger on scroll.

## Steps taken

1. **Read Figma** (read-only `use_figma`). The `.Bubble` main component has a placeholder grey fill; the variants override it to `Surface/surface-black`. The arrow geometry comes from the union's polygon.
2. **API:** ``<cc-tooltip for="trigger-id" placement="top|bottom|left|right">text</cc-tooltip>``.
   - **`placement` instead of Figma's "Direction":** `direction` already means text direction in CSS.
   - **`for` instead of wrapping the trigger:** the tooltip stays a sibling in light DOM, which the description needs (step 4).
3. **Popover and positioning.**
   - The host is `popover="manual"` with `role="tooltip"`, so it renders in the top layer, above every `overflow` and `z-index`.
   - It is placed with CSS anchor positioning (`position-area`). The anchor and tooltip names are set as **inline styles** (`anchor-name` on the trigger, `position-anchor` on the host), because anchor names are tree-scoped: a name set in the shadow stylesheet wouldn't match the trigger in the document.
   - The bubble sits 8px (`gap-1`) from the trigger, so the 6px arrow ends 2px short of it.
4. **Description across shadow roots.**
   - `aria-describedby` IDs can't reach the real `<button>` inside `<cc-button>`'s shadow root. So the tooltip finds the trigger's focusable inner element (`button, a, input, select, textarea` in its open shadow root, or the trigger itself) and sets `ariaDescribedByElements` on it.
   - Element references may point from a shadow root out to the document, so this works for `cc-button`, `cc-link` and native elements alike. Swapping the anchor and its `anchor-name` happens synchronously. Only setting the description waits, for `customElements.whenDefined` and `updateComplete`, so a trigger element defined later still gets it. The tooltip's anchor name is added to the trigger's `anchor-name` list, so an author's own name and other tooltips on the same trigger are kept. Changing `for` or removing the tooltip removes the reference and the anchor name.
5. **Events:**
   - The tooltip listens on its own root node (the document or a shadow root), not on the trigger. It recognises the trigger by `for` in each event's `composedPath()`. So a trigger rendered later, re-rendered, or a tooltip moved in the DOM keeps working, and there are no per-trigger listeners to leak.
   - Hover (trigger or tooltip) and focus are tracked separately. It hides 100ms after the last of them ends, which keeps it hoverable across the 8px gap. Blur with no hover hides it at once.
   - Escape only acts while it is open, and calls `preventDefault()`, so a surrounding `<dialog>` stays open.
6. **Public `show()` / `hide()`** for programmatic use (the AllVariants story uses them).
7. **Stories:** Default (on a `cc-button`), Bottom, and AllVariants (all four placements open at once).
8. **Tests:** `cc-tooltip.test.ts`, 13 tests at first (21 after the review):
   - defaults;
   - hover shows it and leaving hides it;
   - moving onto the tooltip keeps it open;
   - focus, Escape and blur;
   - the description on a native button and on a `cc-button`, read from **Chrome's accessibility tree** through `cdp()` (`toHaveAccessibleDescription` doesn't understand element reflection);
   - changing `for`;
   - colours, text and padding;
   - each placement: 8px gap, centred, arrow on the facing side;
   - cleanup on removal.
9. **Registered** in `src/index.ts`, the `exports` (`./tooltip.js`) and the README.

## Verification

- `vitest`: 101/101 pass, 13 of them for the tooltip (before the review). `tsc` is clean, and `npm run build` succeeds. The manifest includes `cc-tooltip`.
- **Storybook against the Figma screenshot:** all four placements match, including the arrow positions. Tab on the trigger shows the tooltip and Escape hides it.

## Left out

- **JS positioning fallback:** the plan says "anchor positioning where supported, with a small JS fallback". Chrome, Edge, Safari 26 and Firefox 147+ all support anchor positioning now, so I left the fallback out. Add it if older browsers must be supported.
- **Flipping when there is no room** (`position-try-fallbacks`): the arrow would have to flip too. Add it when needed.
- **Show delay and long text wrapping:** it shows instantly and the text doesn't wrap. Figma defines neither.
- **`aria-describedby` set on the trigger's inner element later:** that element's own attribute replaces the reflected reference, so the tooltip is no longer read. This is how element reflection works; set descriptions on the trigger only through the tooltip, or re-set `for`.
- **Disabled `cc-button` triggers:** they can't be focused, so keyboard users don't see the tooltip. Hover works.
- **Touch:** there's no long-press; tooltips shouldn't hold essential information on touch devices anyway.

## Designer questions

- `Surface/surface-black` isn't in the exported tokens (`tokens.css`). The CSS uses `var(--cc-surface-surface-black, var(--cc-palette-black))` until the token export is refreshed.
- Should the tooltip sit further from the trigger? At 8px, the arrow tip touches a focused `cc-button`'s focus ring.

## Follow-up: tooltips opening on the wrong story

On the Storybook docs page, hovering one story's button opened the tooltips of other stories too. Two causes:

1. **Duplicate ids in the stories.** Every story used `id="trigger"`. Since the review fix, the tooltip matched *any* element in the event path with that id. It now matches only the element `getElementById(for)` resolves to, the same rule as `<label for>`. The stories generate unique ids. There's a test with two elements sharing one id.
2. **AllVariants opened every tooltip on the page.** Its `show()` call queried all `cc-tooltip` elements in the document, which on the docs page includes Default and Bottom. It now only opens its own (`for^="all-variants-"`).

Checked on the docs page: each button shows only its own tooltip, and nothing opens on load. 110/110 tests pass.
