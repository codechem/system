# cc-dialog

## Goal

Build `<cc-dialog>`, the Wave B dialog from the plan, from the Figma "Dialog" component (file `K7Z7bb2IjqiyDjik5qjEoN`, component `378:2902` on the "Dialogs" page). The link given, node `382:668`, is the page's documentation frame named "Dialog". The plan says: build it on the native `<dialog>` with `showModal()`.

## Requirements

### From Figma

The node is a single loose `COMPONENT`, not a component set. It has no variants, only boolean and text properties, and it nests three other components: Text Input (Wave C, not built), List item (`cc-list-item` exists) and Button (`cc-button`).

Built as a dialog shell. Its body content (selector, list) is the consumer's, so it sits in a slot.

| Figma property | Built as |
|---|---|
| Text Dialog title ("Dialog title") | `heading` attribute, rendered as `<h2>` |
| Show Dialog title (BOOLEAN, default true) | Omit `heading` (no off switch; the text is the switch) |
| Text Description (TEXT) | `description` attribute |
| Show Supporting text / Show Title + Description (BOOLEAN, default true) | Omit `description` / `heading` |
| Show Selector List, Show List, Show Text Input (BOOLEAN, default true) | Content in the default slot; the consumer decides what is there |
| Show Buttons, Show Secondary button (BOOLEAN, default true) | Content in the `actions` slot |

Measurements, all read from the Figma API and bound to tokens:

| | Value | Token |
|---|---|---|
| Frame width | 448 | none exists, raw `448px` (capped at viewport minus 2 × `padding-3`) |
| Corner radius | 4 | `--cc-radius` |
| Padding (all sides) | 24 | `--cc-padding-padding-3` |
| Gap between title, description and body | 40 | `--cc-gap-gap-5` |
| Gap between title and description | 20 | `--cc-gap-gap-2-5` |
| Gap between buttons | 16 | `--cc-gap-gap-2` |

The buttons sit at the right edge (`justify-content: flex-end`), as on the screenshot.

### Expected behaviour

- `open` shows the dialog as a modal (`showModal()`), with the rest of the page inert. Removing `open` closes it.
- Escape closes the dialog. `open` is removed and `close` is fired.
- On open, focus moves to the first focusable control.
- Tab and Shift+Tab stay inside the dialog and wrap at both ends.
- The dialog is named by its heading (`aria-labelledby`). Without a heading, `aria-label` is forwarded to the inner dialog.
- An empty body or actions area takes no space (no 40px gap).

## Steps taken

1. Read the Figma node: `use_figma` read-only inspection of the page and of the loose component, plus a screenshot.
2. Checked every bound variable against `packages/tokens/dist/tokens.css`. All exist.
3. Read the house conventions (`cc-button`, `cc-checkbox`, `cc-link`, `cc-accordion`, `icon-styles`) and the accordion stories and tests.
4. Wrote `cc-dialog.ts`, `cc-dialog.stories.ts` and `cc-dialog.test.ts`.
5. Registered the component in `index.ts`, `package.json` exports and the README (what's inside, project layout).
6. Found three problems while testing, and fixed them:
   - **Initial focus was lost.** The body and actions wrappers were hidden until `slotchange` fired, which is after the first render. `showModal()` ran while the slotted buttons were `display: none`, so focus went nowhere. Fix: `hasBody` and `hasActions` are now derived from the light DOM during render, so the first paint is already correct.
   - **Chrome's modal does not trap Tab.** The plan assumed focus trapping "comes free". A probe showed that Tab from the last control moves focus to the browser (`BODY`) once before wrapping. The WAI-ARIA dialog pattern requires the trap, so the dialog now wraps Tab and Shift+Tab itself.
   - **`cc-button` does not set `delegatesFocus`.** Calling `.focus()` on its host does nothing, so the wrap would strand focus on the last button. The wrap now focuses the host's inner focusable element when there is one.
7. Fixed the test bugs the failures exposed: the size table had its arguments in the wrong order, the test viewport (≈414px wide) capped the dialog width (set to 1280px for the sizes block), and `cc-button` was not registered in the test file.
8. Storybook: the root script `npm run storybook -- --no-open` fails, because npm reads `--no-open` as its own config flag inside the workspace chain. I started Storybook directly from `apps/storybook` with `npm exec -- storybook dev -p 6006 --ci --no-open`.

## Left out

- **Text Input** (the "Choose…" selector in the Figma body). It is Wave C and not built. The body is a slot.
- **List item rows with a close (×) icon.** `cc-list-item` exists, but it has no close affordance, and Figma's rows are 40px tall. Rows are the consumer's content.
- **Close (×) button on the dialog.** It is not in the Figma frame.
- **Dismiss on backdrop click.** No behaviour is specified.
- **Animation and `prefers-reduced-motion`.** The dialog has no transition.
- **Visual snapshot test, axe check, screen reader spot check, Code Connect mapping, changeset, React and HTML sandboxes.** These are in the plan's Definition of Done, not in this skill's checklist. They are not done here.
- **`cc-button` `delegatesFocus`.** Adding it belongs to the button component. Until then the Tab wrap reaches the inner button through `focusInside()`, but other focus calls on `cc-button` remain as they were.

## Designer questions

1. The description in Figma has a line break after the first sentence and a double space ("need them  in the future"). Built as one string with single spaces. Which copy is correct?
2. The Figma frame has no backdrop, but a modal needs one. Built with `--cc-scrim-scrim-50`. Is that the intended scrim?
3. The list rows have a × icon and a 40px pitch. Is the × a `cc-list-item` state, or part of the dialog?
4. The dialog has no close (×) button in Figma. Is one intended, or is closing only by buttons and Escape?
5. The width is fixed at 448px. Is there a mobile width rule?
6. The Figma node is a loose component, not a component set. Should it be published as one, so future variants fit the same pattern?

## Review

**Verdict (first pass): Ready with fixes.** The reviewer ran in a scratch copy and did not modify the repo. Its probes confirmed:

- Open and close sync, Escape, reopening in the same tick: no double `close` events, no stuck state.
- Shift+Tab between `cc-checkbox` and `cc-button` wraps both ways.
- Text, comment and whitespace children are handled correctly by `hasBody` and `hasActions`.
- Conventions match `cc-button`, `cc-accordion` and the test imports; the 448px width is the only raw measure.

Findings and what was done:

| Severity | Finding | Fix or reason left |
|---|---|---|
| Important | A disabled or hidden last control made Tab escape to `body`, because the focusable list kept controls that cannot take focus. | Fixed. `focusables()` skips `disabled` and zero-rect elements. Tests: "skips a disabled last control", "skips a hidden last control". |
| Important | Initial focus did not reach a `cc-button` first control; focus stayed on the dialog. Cause: the dialog's `updated()` runs before the button's shadow root renders, so `focusInside` found no inner button. | Fixed. `focusWhenReady()` waits for the control's `updateComplete` first. The test asserts initial focus. |
| Minor | "wraps Tab between custom-element controls" did not check initial focus, so it passed through the `outside` path. | Fixed. It now asserts initial focus. |
| Minor | No Shift+Tab test for custom-element controls. | Fixed. "wraps Shift+Tab between custom-element controls" added. |
| Minor | The spec overclaimed focus behaviour for disabled, hidden and custom-element-first cases. | Fixed by the changes above; the spec's expected behaviour now holds and is tested. |
| Minor | `aria-label` stays on the host as well as the inner dialog. | Left. The host has no role, so this is harmless. |
| Minor | Default story has `open: true`, so Storybook opens the modal on the docs page. | Left. The Figma frame is an open dialog, so the default shows it. Escape does not update the `open` control, which is a Storybook limitation of controls. |
